# Player levels and account XP

## Rules

- **Exactly 1,000 XP per level forever**, starting at Level 1 and 0 total XP.
- `level = Math.floor(totalXp / 1000) + 1` and progress is `totalXp % 1000`.
- Player level is **not** Ranked RP or a competitive matchmaking rating.
- New server-verified Ranked wins give **125 XP**. After the separate Ranked outcome XP receipts migration, genuine recorded Ranked losses give **10 XP**. Both use the same one-award-per-match ledger.
- Guest games and browser-recorded Practice wins give **0 account XP** until a secure earning policy is designed. Practice result displays and personal-best tracking do not change.
- Existing historical Ranked results are **not backfilled**, avoiding duplicate/unsupported rewards.

## How rewards stay trustworthy

Only the existing server-owned Ranked win path can insert into `public.ranked_verified_results`. The database trigger `xp_internal.award_verified_ranked_xp()` reacts to that insert; the browser never submits XP or calls this function. The private ledger has one primary-key row per `source_match_id`. The balance update and reward insertion happen in one transaction. Database grants and RLS allow account owners to **read only their own total**. No public INSERT, UPDATE, DELETE, or reward RPC exists.

The UI queries `public.player_xp_profiles` with the signed-in Supabase session. Accounts with no wins have no row and therefore show Level 1 / 0 XP. If the XP table is missing or the query fails, the UI shows an unavailable state, **not** a fabricated XP value.

## Deployment — staging first

1. The patch installer fills a migration file generated by the Supabase CLI (`npx supabase migration new player_levels`). Never manually invent migration timestamps.
2. Confirm the target database already has the actual `public.ranked_verified_results` trigger and appropriate server-side permissions. The migration **fails closed** if this table is missing or the XP schema already exists.
3. **Do not apply migrations to the production project automatically.** Deploy to a nonproduction staging database following `docs/RANKED-STAGING-DEPLOYMENT.md`, and coordinate with the database maintainer before any production change.
4. Verify `player_xp_profiles` RLS with two different signed-in accounts: user A must not read user B's total, and `anon` must be unable to read any totals.
5. Verify `anon` and `authenticated` cannot INSERT/UPDATE/DELETE the profiles or ledger and cannot directly invoke the private XP trigger function.
6. Complete a genuine new Ranked victory through the existing backend. Confirm exactly 125 XP and a single ledger row. Rechecking/retrying the result must not double-pay. Confirm a loss, a direct forged POST, and a client-originated Practice win award no XP.
7. Use a rollback-capable staging transaction for further concurrency tests and inspect database advisors before production deployment.

### Suggested read-only verification queries

```sql
select user_id, total_xp, updated_at from public.player_xp_profiles order by updated_at desc limit 20;
select user_id, source_match_id, amount, awarded_at from xp_internal.player_xp_ledger order by awarded_at desc limit 20;
```

These are maintenance queries for an authorized database administrator. Never expose the ledger to a browser client. The UI shows a friendly error until the reviewed migration is deployed to the database used by the application.

## Future work

- Design server-verifiable Practice XP, if desired, without trusting arbitrary browser boards.
- Consider account level-up feedback and a compact level indicator next to the username after the profile card and verified rewards are tested in staging.
- Add explicit capped rewards for other server-controlled events once their abuse cases are reviewed; update this document and use a new migration for rule changes.

## Verified Ranked outcome receipts

A later **staging-first** migration (`ranked_outcome_xp_receipts`) adds three connected capabilities:

- New server-confirmed Ranked losses earn **10 XP**; existing verified Ranked wins still earn **125 XP**.
- The private `xp_internal.player_xp_ledger` remains one row per Ranked match. Only the trusted server-owned Ranked move and win triggers can award XP. An `AFTER INSERT` trigger on the ledger writes an owner-readable receipt in the **same transaction**.
- The signed-in player may **SELECT only their own** rows from `public.player_xp_match_receipts` under RLS. No client or service-role INSERT, UPDATE or DELETE is permitted on that table. The result dialog shows an earned amount only when it can read and validate an actual receipt for that match.

Existing wins/losses do not receive new receipts or retroactive XP. A missing receipt is displayed as missing, never interpreted as a zero-XP award. The new result UI can be merged while the migration is pending, but meaningful receipt data only appears after the migration is deployed and a fresh verified match is completed.

Before deploying beyond staging: confirm both direct-reveal and chord losses award exactly once, victories still award 125 XP, ledger/receipt creation rolls back atomically on errors, other users cannot see or mutate rewards, forged API calls and duplicate moves award no XP, and schema/permission advisors report no relevant regressions. Competitive RP and browser-recorded Practice XP remain separate future work.
